# Security Model

The migration generated by p9s decides who can change the permission graph, and how the caches stay correct. This page describes those guarantees and the rules your application has to follow for them to hold.

## Database roles

| Role                          | Configured in        | Can do                                                                                   |
| ----------------------------- | -------------------- | ---------------------------------------------------------------------------------------- |
| Migration owner               | whoever runs the SQL | Owns every p9s object. Bypasses RLS on the tables it owns.                               |
| Graph writers                 | `engine.graphWriters` | Insert, update and delete edges and assignments. Run backfill and enable/disable functions. |
| Application users             | `engine.users`        | Read edges, assignments and caches. Write business rows as their RLS policies allow, which moves their home edges. |
| Everyone else                 |                      | Nothing, p9s revokes its tables and functions from `public`.                             |

`graphWriters` defaults to an empty list, in which case only the owner can change edges and assignments. Application users are read-only on them on purpose: if the role that runs end-user queries could insert into `assignment_edge`, any user could grant themselves access to anything. Share and invite actions should go through a backend role listed in `graphWriters`, or through `security definer` functions that check the caller's rights first.

## Nodes are rows

There are no node tables: every row of a resource table is a resource node, and every row of a role table a role node. Its id is the table's `resourceId` (or `roleId`) column, which p9s adds, fills for existing rows and gives a default. The caches hold one row `(id, id)` per node, and that is how p9s knows which ids exist:

- An edge or assignment must connect ids of existing rows. Edges and assignments have no foreign keys, triggers check them instead and raise `foreign_key_violation` errors.
- Deleting a row deletes the edges and assignments it has, so the next row given the same id inherits nothing.
- An insert whose id is already used by another row, of any bound table, is rejected, and so is an update changing an id.

**Ids.** In integer mode the resource tables share one sequence, `resource_id_seq`, and the role tables another, `role_id_seq`, so ids are unique across tables. A column with ids of its own would collide with the other tables, so the migration refuses to bind an integer column that has its own default (a `serial`, for example), is an identity column or is generated, and stops before changing anything. Keep that column as it is, and bind a separate column for p9s instead, like `resourceId: "resource_id"`, which p9s adds. Rows inserted with explicit ids don't advance the sequence: after such a bulk load, move it past them with `select setval('resource_id_seq', (select max(...) ...))`. In UUID mode the default is `uuid_generate_v4()`.

## Home edges and shares

A table with a parent column (`resourceParent` / `roleParent`) has one *home edge* per row with a parent, from that parent to the row, with every permission bit set. p9s writes it from the triggers of the table: inserting a row creates it, changing the parent column moves it, and setting the column to `null` or deleting the row removes it. Index the parent columns: p9s looks rows up by them on every write.

Other edges are *shares*, written by graph writers to link a node under more parents, or to restrict a path with fewer bits. The `home` column of the edge tables tells them apart, and a trigger keeps clients from forging or removing home edges:

- Inserting an edge with `home = true`, or setting `home = true`, is rejected.
- Updating a home edge, for example to change its bits, turns it into a share: `home` becomes `false`, and p9s stops moving or removing it with its row. The row's next parent change then adds a new home edge.
- Deleting a home edge is rejected. Move or delete its row, or first make it a share with `update ... set home = false`.

**Inserting and moving rows.** A new row has no permission of its own, it gets them from its parent. So an application user can only insert a row with a parent, under which they have the table's `insert` bit. Moving a row is inserting it under its new parent: the `update` policy checks the `update` bit on the row and the `insert` bit on the new parent, unless an edge already links that parent to the row. Rows without parent are created by the owner, or by a `security definer` function, and reached through shares and assignments.

**Leaf rows.** A row of a leaf table (`resourceLeaf`) has exactly the permissions of its parent: every policy of the table checks its bit on the parent. Inserting one needs the `insert` bit on the parent. A leaf row has no node, so no edge tells whether an update changed its parent: every update checks the `update` bit on the parent of the row before and after the update. Moving a leaf row thus needs the `update` bit on both parents, rather than the `insert` bit on the new one. When the update has a `where` or `returning` clause, Postgres also checks the new row against the `select` policy, which then needs the `select` bit on the new parent. Users cannot move a leaf row out of every parent.

Nobody except p9s writes to the cache tables (`resource_edge_cache`, `role_edge_cache`, `assignment_edge_cache`). They are maintained by `security definer` triggers owned by the migration owner, which pin `search_path` to `engine.schema, pg_temp` so that a temporary table cannot shadow a p9s table.

Re-running the migration re-applies these privileges, and revokes broader grants left by older versions.

## Rules for the application

- **Run the migration with `engine.schema` as the current schema.** The migration refuses to run otherwise, because the p9s objects are created unqualified.
- **Write the graph in `READ COMMITTED` transactions** (the Postgres default). Every graph write takes a transaction-level advisory lock, so that two concurrent writes can't each compute the caches from a graph that is missing the other one's edge. That only works if a transaction sees rows committed while it was waiting for the lock, so graph writes in `REPEATABLE READ` or `SERIALIZABLE` transactions raise an error. Graph writes include inserting a row with a parent, changing a parent column and deleting a row. Inserting a row without parent, updates that change no parent column, and every write to a leaf table don't take the lock.
- **Don't `TRUNCATE` p9s-managed tables.** The p9s triggers do not fire on `TRUNCATE`, so the caches would keep stale access. A trigger rejects it on edges, assignments and bound tables: delete rows instead, or disable the triggers, truncate, and enable them again.
- **Bulk loads**: call `resource_trigger_disable()` / `role_trigger_disable()` (and `assignment_trigger_disable()` when `combineAssignmentsWith` is not `none`), load rows, edges and assignments, then call the matching `*_enable()` functions. They create the home edges of rows loaded with a parent, check that ids are unique and that edges and assignments connect existing rows, and rebuild the caches. Edges loaded with `home = true` are taken as the home edges of their child rows.

## Permission bits

A permission is a bitmap of `engine.permission.bitmap.size` bits. The numbers in a table's `permission` config are bit positions counted from the left: bit `0` is the first character of `b'1000…'`. A policy for bit `n` checks `(permission << n)::bit = b'1'` on every cache or edge along the path, so access requires the bit on every edge of at least one path from the user to the resource.

Roles that are not listed under a table's `permission` get no policy on that table, so RLS denies them every row. That includes graph writers, which usually know the ids they need and don't have to read business tables through RLS.
