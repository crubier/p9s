# p9s example: a team workspace

A Notion-like app built with Next.js, Drizzle and Better Auth, where Postgres decides every permission. Organizations have members and teams. Their spaces hold nested folders, documents and comments, which members share with each other. Members can also call a REST API with keys that act as them. Admins read an audit log of every change, and can view or act as any member.

The server never filters rows itself. It runs each request as the `app_user` database role, with the role id of the member in a transaction setting, and RLS policies generated by p9s let through what that member may see and change.

## Run it

You need Postgres 14 or later, and a role that can create roles: the migration creates `app_user` and `app_backend`.

```bash
createdb p9s_example
cd examples/nextjs-drizzle
export DATABASE_URL=postgresql://postgres@localhost:5432/p9s_example
export BETTER_AUTH_SECRET=$(openssl rand -base64 32)
export BETTER_AUTH_URL=http://localhost:3000
bun run db:migrate   # Drizzle migrations, then migrations/p9s.sql and migrations/audit.sql
bun run db:seed      # Acme, then 3000 mock users in Globex and Initech, in under a minute
bun run dev
```

`bun run db:seed --users 300` seeds fewer mock users, `--users 0` none, and `--documents-per-member 10` fewer documents.

Then open http://localhost:3000 and sign in, with the password `password1234`, as one of the Acme accounts listed on the sign-in page:

| Person | Can do |
| --- | --- |
| alice@acme.test | Admin of Acme: everything, including members, teams and the access overview |
| bob@acme.test | Engineering team: edits Engineering and General, views Design, comments on one Leadership document |
| carol@acme.test | Design team: edits Design and General, comments in Engineering |
| dave@acme.test | In no team: General only |
| erin@acme.test | Contractor: General, and the Runbooks folder of Engineering shared with her |

### Mock users

The seed also creates `user0001@example.test` to `user3000@example.test`, all with the password `password1234`. The sign-in page signs you in by number. What each user is follows from their number alone, as [`src/mock/people.ts`](./src/mock/people.ts) explains:

- Users 1 to 2400 are members of Globex, 2101 to 3000 of Initech, so 2101 to 2400 are in both.
- In each organization, the first 5 members are admins: `user0001` at Globex, `user2101` at Initech.
- Every 25th member is a guest, in no team: `user0025`, `user0050`, and so on. They see what everyone sees, and a few folders and documents shared with them.
- The others are in a department, by their number: at Globex, `user0011` is in Engineering, `user0012` in Product, `user0013` in Design. Each department has a space its team edits, and that the next department's team can view. The first of each department in every 200 members (100 at Initech) leads it, with full access to its space and a seat in Leadership.
- Members are also in squads of 6 to 16, each with a project space. Half of these spaces are visible to everyone.

Spaces hold about 4400 folders, nested up to 5 deep, and 132,000 documents at Globex, with comments and shares: a member of a department reads about 100,000 of them. The database takes about 400MB. Then [`src/mock/generate.ts`](./src/mock/generate.ts) plays a month of activity through the same functions as the app: edits, comments, moves, shares, team changes, impersonations and API calls, which fill the audit log. The data is the same on every run.

### The API

The seed prints an API key of Bob's. Every 20th mock member also has a key: `p9s_globex_user0001` for `user0001` at Globex.

```bash
curl -H "Authorization: Bearer $KEY" "http://localhost:3000/api/v1/documents?limit=50"
curl -H "Authorization: Bearer $KEY" "http://localhost:3000/api/v1/documents?limit=50&after=$NEXT"  # the next of the previous page
curl -H "Authorization: Bearer $KEY" -H "content-type: application/json" \
  -d '{"folderId": "...", "title": "From the API"}' http://localhost:3000/api/v1/documents
```

### Viewing as someone else, and the audit log

On the members page, an admin can **view as** a member: the app shows the organization exactly as RLS shows it to them, in read only transactions, so Postgres refuses any change. **Act as** lets the admin change things on their behalf, which the audit log records as done by the member, by the admin. A cookie names the member, and every request checks again that the signed-in user is an admin, so it stops working as soon as they are not. API keys stay their owner's own: an admin acting as a member cannot create or revoke them.

The **audit log** of each organization is filled by the triggers of [`migrations/audit.sql`](./migrations/audit.sql), on folders, documents, comments, teams, members, and the shares and team memberships of the p9s graph. They know who made the change from the settings of the transaction: the member's role id, or their API key's, and the admin acting as them. They copy names, so the log still reads well after a deletion. The audit table is a p9s leaf of the organization, readable with the admin bit, so RLS shows it to admins only.

`bun run test` runs the permission scenarios of [`test/permissions.test.ts`](./test/permissions.test.ts) on a new database, when `P9S_TEST_DATABASE_URL` points at a server where it can create one.

## How it is built

### The permission graph

```
Resources                                   Roles

Acme (organization)                         Acme (organization): everyone in it
├── Admins, Engineering, Design (teams)     ├── Alice, Bob, Carol, Dave, Erin (members)
├── Alice, Bob, Carol, Dave, Erin (members) │
└── General, Engineering, Design,           Admins, Engineering, Design (teams)
    Leadership (spaces)                     └── their members, through role edges
    └── folders
        └── documents
            └── comments (leaf rows)        API keys (leaf rows of their member)
```

The p9s configuration is in [`src/p9s.ts`](./src/p9s.ts):

- **Organizations** are the root of both trees. The server creates them, with an Admins team assigned every bit on the organization, and everyone in it assigned the directory bit.
- **Members** are rows of `member`, the role a user acts as in one organization. They are children of their organization in both trees, through the same `org_id` column, so RLS decides who adds and removes them: the admin bit on the organization. This is the "roles as resources" pattern of the [security model](../../website/docs/configuration/security-model.md).
- **Teams** are resources in their organization, so admins create and delete them through RLS, and roles whose members are role edges. Adding someone to a team writes a role edge, which only the graph writer role can do: the server checks that the member is an admin, then writes it as `app_backend`.
- **Folders** are in a folder, or at the top of the organization, then called spaces. p9s follows one parent column per table, so a trigger of [`migrations/0001_app.sql`](./migrations/0001_app.sql) copies the resource id of the one the folder is in into `parent_resource_id`, the column p9s follows.
- **Documents** are in a folder, and hold the organization of their folder in `org_id`, which a foreign key on both columns keeps right: requests made in an organization find its documents with it, even those whose folder RLS hides. **Comments** are leaf rows of their document: they are not in the graph, and have exactly the permissions of their document.
- **API keys** are role leaf rows of their member: they have their own role id, so the server knows which key made a request, and the permissions of their member.

### Permission bits

[`lib/permissions.ts`](./lib/permissions.ts) names the 8 bits. Each table maps its operations to some of them:

| Bit | Name | Checked on |
| --- | --- | --- |
| 0 | read | select folders, documents and comments |
| 1 | create | insert folders and documents in a folder, spaces in the organization |
| 2 | edit | update folders, documents and comments |
| 3 | delete | delete folders, documents and comments |
| 4 | comment | insert comments |
| 5 | share | checked by the server before it shares |
| 6 | directory | select the organization, its teams and members |
| 7 | admin | insert, update and delete teams and members |

Everyone in an organization has the directory bit on it. Bits flow down the tree, so it reaches every space too, but folders check bit 0 to be read: seeing who is in the organization does not show its spaces.

### Requests

[`src/db.ts`](./src/db.ts) connects as the owner of the tables, which bypasses RLS, for Better Auth and for the lookups the server makes on its own behalf. [`src/service.ts`](./src/service.ts) holds what the app does, each function acting as a member:

- `asRole(actor, fn)` runs `fn` in a transaction as `app_user`, with `app.role_id` set to the member, or API key, for `current_role_id()`, and `app.impersonator_member_id` to the admin acting as them, for the audit log. The settings end with the transaction, so a pooled connection never keeps someone's identity. When an admin views as someone, the transaction is read only.
- Reads are plain queries: `select ... from folder where parent_id = $1` returns the folders the member can read. `resource_permission(resource_id)` tells what they can do with each row, to show the right buttons.
- Writes are plain inserts, updates and deletes. RLS rejects what the member may not do, and the error becomes a "You don't have permission" message.
- `app_user` cannot read the graph tables, only its own part of the graph, through the [views of the current user](../../website/docs/configuration/security-model.md#what-users-see-of-the-graph): "Shared with me" reads `current_assignment`, and moving a folder checks that it does not go inside itself with `current_resource_edge`. Who is in a team, and who has access to a document, are read as `app_backend`, by `readGraph`, after checking as the member that they may see the team or the document.
- Shares are assignments, which members write themselves with `resource_share` and `resource_unshare`: folders and documents have a `share` bit, and p9s refuses to give bits the member does not have. The server checks the same first, only to tell why it refuses. Team memberships are role edges, which the server writes as `app_backend` after checking that the member is an admin. Folders and documents have `manageAccess` on the read bit: whoever reads one lists who has access to it from the `resource_access` view, and the [access overview](./app/o/[org]/access/page.tsx) asks `resource_permission(resource_id, role_id)` about every member as `app_user`, since admins read every space.

Two things to know when writing such an app:

- Don't insert rows of a node table with `returning`: Postgres checks the new row against the select policy before p9s gives it its edges, and rejects it. Give rows their id beforehand, as `createFolder` does.
- Drizzle returns timestamps of raw SQL queries as strings.
