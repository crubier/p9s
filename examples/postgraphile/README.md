# p9s example: a team workspace on PostGraphile

The workspace of [`examples/nextjs-drizzle`](../nextjs-drizzle), built on [PostGraphile](https://postgraphile.org) 5 instead: organizations with members and teams, spaces of nested folders, documents and comments, sharing, an access overview, API keys, an audit log, and admins viewing or acting as members. The React front end only talks to GraphQL, and every page has an **Open in GraphiQL** button, with the query of the page and its variables, which runs as the signed-in user. It runs on [p9s-example-postgraphile.vercel.app](https://p9s-example-postgraphile.vercel.app), with the full seed.

PostGraphile builds the whole API from the database: the tables, the views of p9s and the functions of [`sql/app.sql`](./sql/app.sql). There is no resolver. Every request runs as the `app_user` database role, with the role id of its member, and the RLS policies generated by p9s let through what that member may see and change. `engine.postgraphile: true` in [`src/p9s.ts`](./src/p9s.ts) adds the rest, see [PostGraphile](../../website/docs/configuration/postgraphile.md).

## Run it

You need Postgres 15 or later, and a role that can create roles: the migration creates `app_user` and `app_backend`.

```bash
createdb p9s_postgraphile
cd examples/postgraphile
export DATABASE_URL=postgresql://postgres@localhost:5432/p9s_postgraphile
export BETTER_AUTH_SECRET=$(openssl rand -base64 32)
export BETTER_AUTH_URL=http://localhost:3200
bun run db:migrate   # sql/schema.sql, then sql/p9s.sql, sql/app.sql and sql/audit.sql
bun run db:seed      # Acme, then 3000 mock users in Globex and Initech, in about a minute
bun run dev          # the app on http://localhost:3200, GraphiQL on http://localhost:3200/graphiql
```

`bun run db:seed --users 300` seeds fewer mock users, `--users 0` none, and `--documents-per-member 10` fewer documents. `bun run build` then `bun run start` serves the built app.

Sign in with the password `password1234`, as one of the Acme accounts listed on the sign-in page, or as a mock user by number. They are the people of the Next.js example, with the same data: see [its accounts](../nextjs-drizzle/README.md#run-it) and [mock users](../nextjs-drizzle/README.md#mock-users). A member of a Globex department reads about 100,000 documents.

## GraphiQL

GraphiQL, on `/graphiql`, sends the session cookie of the app: it asks as whoever is signed in, and RLS shows them what it shows them in the app. The `x-p9s-org` header names the organization they act in, by its slug; the button of each page fills it. What to try, in Acme as Bob:

```graphql
{
  currentMember { name permission }
  organizationBySlug(slug: "acme") {
    spaces { nodes { name permission } }
    sharedDocuments { nodes { title permission } }
    searchDocuments(query: "plan") { totalCount nodes { title path { nodes { name } } } }
  }
}
```

`permission` is the bitmap of `resource_permission` for the member on each row, see the [permission bits](../nextjs-drizzle/README.md#permission-bits). Who has access to a folder, and where it was given, for whoever can read it:

```graphql
query ($id: UUID!) {
  folderByRowId(rowId: $id) {
    name
    access { nodes { name kind permission direct fromName } }
  }
}
```

Writes are mutations: `createFolder`, `moveFolder`, `createDocument`, `updateDocumentByRowId`, `createComment`, `shareResource` with an access level, and for admins `inviteMember`, `createTeam`, `setTeamMembership` and `startImpersonation`. RLS refuses what the member may not do, and the error says why, with the Postgres code: `42501` for a refusal, `25006` for a write while viewing as someone.

### The API

API keys act as their member, with a bearer token, on the same endpoint. The seed prints one of Bob's, and every 20th mock member has one: `p9s_globex_user0001` for `user0001` at Globex. A key belongs to one organization, so it needs no `x-p9s-org` header:

```bash
curl -H "Authorization: Bearer $KEY" -H "content-type: application/json" \
  -d '{"query": "{ currentMember { name } allDocuments(first: 5) { totalCount nodes { title } } }"}' \
  http://localhost:3200/graphql
```

## How it is built

The tables, the p9s configuration and the permission bits are those of the Next.js example, see [how it is built](../nextjs-drizzle/README.md#how-it-is-built). What changes is the server, which is PostGraphile:

- [`sql/schema.sql`](./sql/schema.sql) has the tables of Better Auth and of the workspace, and the roles that requests run as. [`src/p9s.ts`](./src/p9s.ts) binds them to p9s: `bun run db:p9s` writes [`sql/p9s.sql`](./sql/p9s.sql).
- [`sql/app.sql`](./sql/app.sql) is what the API adds to the tables, each function running as the member: the computed fields of the pages (`spaces`, `sharedDocuments`, `searchDocuments`, `path`, `access`, `principals`, `spacePermissions`, `auditEvents`), the creations of node rows, which cannot read back what they insert (see [what PostGraphile needs](../../website/docs/configuration/postgraphile.md#what-it-needs)), and the writes of the graph. Shares are `resource_share` and `resource_unshare`, which members call themselves. Team memberships and impersonations switch to `app_backend`, after checking that the member is an admin. Smart comments hide everything else: the API has no field that writes the graph or the audit log.
- [`sql/audit.sql`](./sql/audit.sql) has the triggers of the audit log, as in the Next.js example.
- [`src/identity.ts`](./src/identity.ts) finds who makes a request: the Better Auth session and the `x-p9s-org` header give the member, or a bearer token its API key. The `p9s-impersonation` cookie, set by the app when an admin starts viewing or acting as someone, is only followed while the signed-in user is an admin of that organization. Viewing makes the transaction read only.
- [`src/graphile.config.ts`](./src/graphile.config.ts) runs every request as `app_user`, with `app.role_id` set to the member's role, or their API key's, for `current_role_id()`. It turns database errors into messages that name no table or policy, and refuses updates and deletes of rows that RLS hides, which PostGraphile would otherwise answer with no row and no error.
- [`src/handler.ts`](./src/handler.ts) serves `/graphql`, `/graphiql` and Better Auth. [`src/server.ts`](./src/server.ts) adds the app, through Vite in development; on Vercel, [`api/index.ts`](./api/index.ts) is the one function and the app is static.
- [`web`](./web) is the app: React, React Router and TanStack Query, with the components of the Next.js example. [`web/lib/operations.ts`](./web/lib/operations.ts) has every query and mutation, typed by [GraphQL Code Generator](https://the-guild.dev/graphql/codegen) from [`schema.graphql`](./schema.graphql): `bun run schema` writes both from the database.
- The seed creates Acme through the GraphQL API, as its people. The mock organizations are written in bulk, then their month of activity goes through the API again.

The front page of an organization asks for its recent documents with the `x-p9s-check-rows` header, which makes p9s check each row rather than collect what the member reads first: that is faster for a page of a large table, and the request is limited to 10ms, after which the app asks again without it.

`P9S_TEST_DATABASE_URL=postgresql://postgres@localhost:5432/postgres bun run test` migrates and seeds a new database, then checks the API as each person, in the process and over HTTP: what they read and can do, sharing, moves, teams, API keys, search, viewing and acting as someone, the audit log, and the masking of errors.
