# p9s example: a GraphQL API with PostGraphile

A project tracker served by [PostGraphile](https://postgraphile.org) 5, where Postgres decides every permission. An organization has people and teams, projects, tasks and comments. People get access to a project or a task through a team or on their own, and whoever manages a project shares it.

PostGraphile builds the whole API from the database: the tables, the views of p9s and a few functions in [`sql/app.sql`](./sql/app.sql). There is no resolver. Every request runs as the `app_user` database role, with the role id of the person in its token, and the RLS policies generated by p9s let through what that person may see and change. `engine.postgraphile: true` in [`src/p9s.ts`](./src/p9s.ts) adds the rest, see [PostGraphile](../../website/docs/configuration/postgraphile.md).

## Run it

You need Postgres 15 or later, and a role that can create roles: the migration creates `app_user` and `app_backend`.

```bash
createdb p9s_postgraphile
cd examples/postgraphile
export DATABASE_URL=postgresql://postgres@localhost:5432/p9s_postgraphile
bun run db:migrate   # sql/schema.sql, then sql/p9s.sql and sql/app.sql
bun run db:seed      # Acme, its people, teams, projects and tasks
bun run dev
```

Then get a token, and open GraphiQL on http://localhost:5678/graphql with it in an `Authorization: Bearer <token>` header:

```bash
curl -X POST localhost:5678/login -d '{"email":"bob@acme.test"}'
```

`/login` gives the token of anyone by their email, to try the API: a real app signs people in first. Set `JWT_SECRET` outside development.

| Person | Can do |
| --- | --- |
| alice@acme.test | Admin of Acme: everything, including the teams |
| bob@acme.test | Engineering team: edits the Website project |
| carol@acme.test | Design team: manages and shares the Brand project, comments on Website |
| dave@acme.test | Contractor: comments on one task of Website, and sees nothing else of it |

Everyone at Acme sees its people and teams.

## What to try

What Bob can do on each project he sees, and on its tasks:

```graphql
{
  allProjects {
    nodes { name permission tasksByProjectId { nodes { title permission } } }
  }
}
```

What was shared with Dave, whatever table it is in:

```graphql
{
  allCurrentAssignments {
    nodes { permission resource { tableName project { name } task { title } } }
  }
}
```

Who has access to a task, and where it was given: anyone who can read the task sees that. A project Dave cannot read shows as a null `assignedResource`.

```graphql
query ($task: UUID!) {
  allResourceAccesses(condition: { resourceId: $task }) {
    nodes {
      permission
      role { tableName person { name } team { name } }
      assignedResource { tableName project { name } }
    }
  }
}
```

Carol shares Brand with Dave, as a viewer. She cannot give more than she has, and Bob, who cannot share Website, gets a row-level security error:

```graphql
mutation ($brand: UUID!, $dave: UUID!) {
  resourceShare(input: { theResourceId: $brand, theRoleId: $dave, thePermission: "10000000" }) { clientMutationId }
}
```

## How it works

- [`sql/schema.sql`](./sql/schema.sql) has the tables, and the roles that requests run as.
- [`src/p9s.ts`](./src/p9s.ts) binds them to p9s. `bun run db:p9s` writes [`sql/p9s.sql`](./sql/p9s.sql) from it.
- [`sql/app.sql`](./sql/app.sql) has the functions of the API: `createProject` and `createTask`, since a node row cannot be created by a mutation that reads it back (see [what it needs](../../website/docs/configuration/postgraphile.md#what-it-needs)), and `setTeamMembership`, which lets admins change teams, as edges are not written by users.
- [`src/graphile.config.ts`](./src/graphile.config.ts) runs every request as `app_user`, with the role id of the token in `jwt.claims.role_id`, which `current_role_id()` reads back for p9s.
- [`schema.graphql`](./schema.graphql) is the API, written by `bun run schema`.

`P9S_TEST_DATABASE_URL=postgresql://postgres@localhost:5432/postgres bun run test` checks the API as each person, in a database it creates and drops.
